# 任务：按下面的骨架写一份企业营销与商业模式分析报告

> **本文件自足** —— 你（AI）读完即按此执行，**不需要任何补充说明**。
> 用户只需把本文件粘给你，不必再写提示词。

## 硬性要求（违反任一条 = 本次不合格，重写该部分）

1. **逐个小点写**：骨架里每一个 `### N.` 小点都必须写，**一个小点都不能省**。写不完就分批。
2. **满足四件套**：每个小点的 `必含` 每一条都要出现；`句式` 照填（**结构不要自创**）；
   `查` 指向的参考档优先使用（拿不到就用自有知识，**并标注「未取得一手证据」**）；
   `反例` 里写的内容**一律不许出现**。
3. **写足字数**：每个小点不低于其标注的字数下限；**宁可分批，不要为了写完而压缩**。
4. **分批输出**：一次写不完就按章输出，每批结束**停下等用户说"继续"**；每批开头先写《流程状态》行。
5. **交付前**：按骨架末尾的《交付前自检表》逐项核对，**原样输出该表并逐项标 ✅/❌**；
   有 ❌ 的部分先修好，**不得**在表里有 ❌ 的情况下声称完成。
6. **不许用"内部注记"充数**：交付稿正文里不得出现 `<!-- -->` 注记、自检表、或任何"我怎么做的"说明。

## 工作流（七步，顺序不可跳）

### 1️⃣ 议题树与假设（先出树，再动手）

```bash
python scripts/issue_tree.py --company "企业名" --type b2c    > 议题树.md   # b2c|b2b|platform
python scripts/issue_tree.py --check 议题树.md                             # 不合格不许进下一步
```
- 顶层分支 3±2，**每条分支写成可被证伪的断言**，并写明「什么数据出现它就作废」
- 必须写一句「**是否遗漏**」检查（证明没漏掉一整块）
- 查 `references/03-方法论操作手册.md` §A 章（诊断类）选模型，只留输出物，不堆框架名词

> ⛔ 没有议题树就写正文 = 不合格（BCG 判据）。免检的唯一情形：用户明说「跳过，直接写」。
>
> ⚠️ **反证条件的判据反直觉**：`issue_tree --check` 数的是**命中了几个不同关键词**（`推翻 / 证伪 / 反证 / 若不成立 / 若不 / 如果为假 / 什么数据会否定`），**不是出现次数**。写十遍「本断言作废」也只算 0 个。稳妥做法：正文里同时出现「**反证条件**」「**被推翻**」「**被证伪**」三处不同措辞（实测 3 个即通过）。
> ⚠️ **反证条件必须写在「章标题 → 第一个 `###` 之间」**（同下方第 4 步的章节级判据坑）——写在小点里等于不存在。

### 2️⃣ 事实检索（只查能证伪假设的信息）

- 检索：年报/财报、官网与公开披露、行业报告（艾瑞/易观/QuestMobile 等）、权威媒体、平台榜单
- 每条数据三级标注：**【已核实】**（有来源+日期）/ **【行业认知】**（多来源一致的公知）/ **【未核实】**（单一来源或无法交叉验证）
- **【未核实】不得进交付稿**；关键数字要 ≥2 个独立来源（三角验证）
- 记录**被证伪的假设**（只留成功项 = 不严谨）
- 查不到就写明「查不到 + 因此该结论降级为定性表述」，不许编
- ⚠️ **「来源：」后面别用「公开」开头**：「来源：公开资料」「来源：公开行业观察」会被 `VAGUE_SOURCES` 判成**泛引用硬错误**（本意是拦「来源：网络 / 据了解 / 据称」，但「公开」开头会一起命中）。
  正确写法：把主体写实——「来源：XX 行业观察，单一来源未交叉验证」「来源：公司 2025 年年度报告及媒体整理的公开行情数据」。
  同理，能被 `has_source` 认可的写法只有 4 类：**带 `【已核实】/【行业认知】` 标记 / 含 URL 或《书名》/ 「来源：<可核验主体>」/ 含「本报告测算、年报、统计公报」等可核验主体词**。
- **引用外部文件时**：先把文件读进来，逐条核对版本号/章节号真实存在（第 8 项门禁）

### 3️⃣ 故事线（ghost deck：先写标题，再填内容）

```bash
python scripts/storyline.py --ghost          # 输出骨架模板
python scripts/storyline.py 报告.md          # 标题通读测试
```
- **每个标题必须是完整结论句**（含谓语，尽量含数字）；主题词标题（「市场概览」「现状分析」）一律不许出现
- ⚠️ **数字必须带单位才被承认为「结论句里的数字」**：白名单＝`% ％ 倍 成 个百分点 万元 亿元 万 亿 元 人 家 个 天 月 年 次 点 条 分`。
  **「150 字」「3 类」「3 项」「7 环」都不算**——这类标题会被判成非结论句，直接拖低「结论句占比 ≥80%」。写标题时优先用 `%` / `亿元` / `人` / `个`。
- 自检：把所有标题单独连读，能读成一个完整论证才算过
- 故事线交用户确认后再展开正文

### 4️⃣ 章节填充（**固定骨架由脚本生成**，用户模板优先）

```bash
python scripts/composer.py --out 骨架.md --tier 全量分析    # 全量分析 | 对标研究 | 尽调式拆解
python scripts/composer.py --out 骨架.md --depth 快档       # **深度档：快档 | 标准 | 深度**
python scripts/composer.py --out 骨架.md --tier 全量分析 --with-guide   # 连关键句片段一起写入
python scripts/composer.py --check 报告.md                  # 填完自检：缺节即不合格
```

> ⚠️ **无代码平台（豆包 / ChatGPT 等）跑不了 `composer.py`** → 直接复制 `skeletons/` 下对应的**现成骨架**（3 体裁 × 3 深度共 9 份，如 `骨架-全量分析-标准.md`），**不要让模型自己编结构**——实测过，那会产出很浅。
> ⛔ **骨架的唯一真相在 `scripts/composer.py`（章节与指引在 `scripts/skeleton_data.py`）——不要手搓结构。**
> 体裁（门禁第 2 项）决定用哪套：**全量分析 17 章 / 46 小点 ｜ 对标研究 12 章 / 34 小点 ｜ 尽调式拆解 14 章 / 36 小点**（三种体裁**都是先「三、商业模式解构」再「四、营销手法拆解」**）。
>
> **骨架是两级的：章（##）→ 小点（###）。拆解深度靠小点承载**（只有章节级骨架时，模型对每章只写一段就交差，拆解深度上不来）：
> - 每个小点都带**四件套（照做，别自由发挥）**：① **必含**（逐项打勾，如「①单客收入算式 ②单客成本 ③毛利 ④真杠杆+理由」）｜② **句式**（照填的骨架句，不是"参考"）｜③ **该查的具体节**（细到 §）｜④ **反例**（明确不要写成什么）
> - **`--check` 拦两种病**：① **缺章**（硬判，不合格）② **小点内容过薄**（低于 **120 字**硬下限即不合格）
> - 「小点偏少」只给 **WARN**（提示可再拆细），**不判死**——真实金标准稿里就有若干章是平铺的，判死会误杀
> - 下限的定位：**防「一句话交差」，不是凑字要求**。写得实就不怕量；写不实才会被拦。可用 `--min-chars` 调下限
> - **骨架含两级目录**（章 → 小点，对应交付模板的「手动目录 1 / 2」样式）；成稿后标题会变成结论句，**出稿前跑 `python scripts/composer.py --toc 报告.md` 重生成目录**
> - **深度档直接决定生成时长**（门禁第 5 项「侧重」时问一句）：**快档**＝每章留 2 小点、目标×0.6（约 3,200 字，快）｜**标准**＝默认（约 8,200 字）｜**深度**＝目标×1.25（12,000 字以上）

**骨架摘要**（完整要求见 `composer.py` 输出；用户给了模板时**逐字沿用用户标题**，本骨架只补缺）：

```
执行摘要（五句话：问题/结论/依据/代价/含义，含数字）
一、核心问题：<结论句 + 数字>（governing question，含量化目标与时限）
二、议题树与假设台账（分支 + 反证条件 + 被证伪记录）
三、外部与内部诊断（**PEST** 宏观 → **波特五力** 行业竞争 → **SWOT** 内外因素清单 → **BCG** 业务结构四象限；SWOT 只列事实，推导在「优势与机会」章）
四、商业模式解构（收入结构 / 单位经济 / 盈利模式与价值链位置 / 模式的脆弱点 / **毛利·流水·ROI 拆解**——模式语言与横向对照查 `references/商业模式库/README.md`）
五、营销手法拆解（**STP** 客群与定位 / **4P** 产品与价格·渠道结构·内容·投放·活动 / 私域与复购手法 / **AARRR** 增长链路 / 打法识别 / 流失点——**10 个小点，手法层主战场**）
六、AI 营销专项（逐项：具体怎么操作 + 证据，不写「积极布局 AI」）
七、AI vs 传统运营对比（逐环节表：传统做法 → AI 做法 → 量化差异）
八、洞察（用户没说出口但一听就认的一句话；至少 1 条非消费者来源）
九、三档情景与敏感性（base/upside/downside + 触发条件 + 反事实或区分相关性/因果）
十、优势与机会（**SWOT 的推导层**：SO/WO/ST/WT 与可执行含义；机会要落到「它能做、别人做不了」）
十一、Red Team：这个结论最可能怎么死（≥3 条反方论点 + 回应）
十二、利益相关者与变革阻力（谁会反对、为什么、怎么处理）
十三、合规与披露（个人信息口径、AIGC 参与说明）
十四、取舍：明确不做的事 + 原因
图表清单（见下方「图表清单怎么写」）
附录：数据来源清单（分「可查证」与「未取得一手原文」两类）+ 版本/作者/署名
```

> ⛔ **填完必须跑** `python scripts/composer.py --check 报告.md` —— **缺节即不合格**（固定骨架的意义就在这）。
>
> ⚠️ **骨架给的占位标题不是结论句，必须自己改写**。骨架里形如「1. 关键变量与取值来源（每个变量都要有出处）」「2. 可验证的差异 vs 不可验证的差异（分开写）」的标题是**指引**，直接照抄会被 `storyline` 判非结论句（拖低 C2 的 ≥80%）。**照填句式、但标题要改成含带单位数字的结论句**——例如「1. 关键变量与取值：5 个变量里 4 个来自半年报原始披露」。
> ⚠️ **骨架与判据有一处已知冲突，必须手工规避**：骨架第二章的小点 1 叫「分支 N｜<结论式断言>」，但 `mbb_audit` 的 A2 只读「章标题 → 第一个 `###` 之间」——**把分支写在小点里必判「议题树 0 支」**。规避方式：分支列表放 `## 二、` 章标题正下方（引言），小点里写分支之间的关系与遗漏检查。同理适用于第五章的合规要素（`mbb_audit` E5 读 `## 十二、` 的章引言）与闭环等式（B7 读第三章章引言）。

> ⚠️ **一条最高频的踩坑：章节级判据只看「章标题 → 第一个 `###` 之间」的正文。**
> `composer --check`、`mbb_audit` 的 A2（议题树分支）与 E3（来源清单条目）**都是这个取法**——它们读的是章节自己的 body，而 `###` 子标题会被当作另一个章节切开。
> **后果**：把「分支 1/2/3…」「来源清单表格」写进 `###` 小点里，就会被判成「议题树 0 支」「可查证条目 0 条」（硬错误），而内容其实一直在文件里。
> **正确做法**：
> - **需要被章节级判据识别的结构**（分支列表、来源清单表格、闭环等式）→ 放在 **章标题正下方、第一个 `###` 之前**（作为章节引言）
> - 小点（`###`）只承载"写实"的论述；小点正文仍须满足 ≥120 字
> - 两处都想要 → 引言放结构（可被识别），小点放论述（满足字数），**内容不要只放一处**

**图表清单怎么写（两条判据互相拉扯，必须同时满足）**：

| 写法 | `chart_check`（要求每条带来源与口径，比例 ≥80%） | `source_ledger`（要求含数字句的来源覆盖率 ≥80%） |
|---|---|---|
| **表格** | ❌ 表头行与 `\|---\|` 分隔行也被算进分母，比例最高只能到 5/7 ≈ 71% | ✅ 表格行被跳过，不计入 |
| **列表 + 每句带「。」** | ✅ | ❌ 一条被句号切成 6 句，只有「来源」那半句合格，其余 5 句全判缺来源 |
| **列表 + 单句（推荐）** | ✅ | ✅ |

**推荐写法**：用 `- 图 N｜<结论句标题> — 回答「…」— 来源：<出处> — 口径：<怎么算的> — 图形：charts/chartN.png — 时点：<时点>`
**整条不含句号/分号**（用「—」分隔），这样它是一句话，来源与口径都挂在这一句上，两个脚本都过。
同一条规则适用于「口径声明」等元信息句：写「（来源：本报告方法说明）」，不要留成无来源的裸句子。

**附录「数据来源清单」怎么摆（踩过的坑）**：

- 来源表格**不要放进 `###` 小节**。`mbb_audit` 的 E3 只取「来源清单」章节标题到**第一个子标题**之间的正文——表格放进小节里等于不存在，会判「可查证条目 0 条」**硬错误**。
  正确做法：小节头用加粗段落（`**A1｜可查证来源**`），把表格留在这个章节自己的正文里。
- 附录里**每条来源所在的那一行要带 URL**（或本书名对应的可核验链接），否则 `cite_resolve` 判「待核验」，可解析率上不去（门槛 90%）。
- 引用外部文件时，报告里用的**书名必须与来源清单逐字一致**；正文里不要用简称（写了《XX 报告》，就不要在别处写《报告》），否则 `cite_resolve` 判**幻影书目硬错误**。

> **样式映射（照填样式名即可）**：章节标题 → `Heading 1`；小节 → `Heading 2 / 3`；正文 → `Normal`；图表题注 → `caption`。**不要手设字体字号行距**——模板已固化（`references/18`）。

**每章末尾必须有一句 so-what**（「这意味着…／因此…」）——答不出「所以呢」的内容，删掉。
加分项（默认做）：AIGC 物料样稿（**必须标注 AI 参与**，规范见 `references/16`）+ 数据洞察图表。

### 5️⃣ 压力测试（交付前自攻一轮）

- **Red Team**：≥3 条最强反方论点，逐条给回应
- **反事实与因果**：必须**显式出现「反事实」字样**并落到数字；若确实不可量化，就明写「**这条对照无法量化**——因为 X 未披露」。只写「本报告区分相关性与因果」**不算**（`mbb_audit` B5 认不到，会判缺量化）。建议给 2–3 条反事实对照，其中一条明确写「无法量化」反而是加分项。
- **Pre-mortem**：写下「如果这份报告 6 个月后被证明错了，最可能错在哪一条假设」
- **敏感性**：核心结论给三档，不给区间 = 假精确
- **陷阱自查**：把互动/声量当结果？用相关性冒充因果？洞察其实是常识？
- **口径自查**：同一指标是否有两个值？分母/时钟/时点是否混用？（对应 B7 硬错误）

```bash
python scripts/mbb_audit.py 报告.md --words 6000 --dep <被引文件路径> --json scorecard.json
```
> ⚠️ **引用了外部文件就必须传 `--dep`**（可多次）。**除了客户/项目文件，还要把「被引用的 skill 参考库」一起传**——若报告里写了「对照 `references/00-打法库.md` 的 §5.8 / §10.5」，那么 `references/00-打法库.md` 就是被引文件，不传它 `cite_resolve` 会把 §5.8 这类章节号判成**幻影引用硬错误**（实测 4 处）。
> 记得把每个 `--dep` 的 sha256 登记进 registry，否则 E6 只能判 ③ 未验证、阻断放行。
> ⚠️ **用 `gate.py` 时 `--dep` 与 `--registry` 必须传绝对路径**。`gate.py` 内部用 subprocess 逐项调用，**cwd 与你的工作目录不同**——传相对路径会找不到 registry，E6 落「③ 未验证」而报「不可放行」，此时报告本身没问题（实测：同一份稿单独跑 `mbb_audit` 判 E6 通过、经 `gate.py` 判未验证，唯一差别就是路径）。
> E6 是**三态**判据，且**①「已验证通过」有硬准入条件**：
> ① **已验证通过** —— dep 可读、引用全部可解析、**且** `--dep-trust auditor`（审计者独立持源）**且** 每个 dep 的 sha256 能在 `assets/dep-registry.json` 里匹配到同名条目
> ② **已验证不通过 = 幻影引用 → 报告硬错误**（打回）——**任何归属下都成立**，引用对不上就是缺陷
> ③ **未验证 → 阻断放行** —— 其余一切情况（未声明归属／哈希未登记／哈希不匹配／路径无效／未传 dep）；属「验证未完成」，**不扣报告分**，但出不了门，且文案必须**指明缺哪一项**
>
> 用法：`python scripts/mbb_audit.py 报告.md --words 6000 --dep <被引文件> --dep-trust auditor --registry assets/dep-registry.json`
> 第 ③ 态的存在是刻意的：**审计者传错路径 ≠ 报告有缺陷**，两者分开显示（`⛔ 硬错误（报告的缺陷）` / `⚠️ 阻断项（验证未完成）`）。
>
> ⚠️ **E6 的能力边界（不许吹）——已从「会被洗白」加固到「只说准话」**：
> · 被审者补交伪造源 → **不再能洗白**（假源哈希不在登记表 → 落 ③ 未验证）
> · **但信任根仍然是人**：谁能敲命令行，谁就能把 `--registry` 指向自己造的表。**限制路径是安全剧场**（有写权限的人照样改表），正确做法是**把「用了哪张表、比了哪个哈希」显示在结论里**，让人能核（E6 输出已强制带 `registry=路径` 与 `sha256=` 前缀）
> · 因此**「已验证通过」仍不等于「引用真实」**——它只等于「与审计者独立持有、且哈希已登记的源一致」。**最终采信要由人签字**（对应「责任边界与签字」第 4 条）
- `mbb_audit` **27 项检查**、5 个维度族（A 结构 25 / B 证据与量化 25 / C 叙事 20 / D 压测 10 / E 治理 20）；其中 **8 项为硬错误**（未核实或未验证数据泄漏 / **口径不自洽 B7** / 主题词标题 / 交付稿缺执行摘要 / 缺可查证来源清单 / 内部过程文档泄漏 / 合规披露缺失 / **引用不可解析 E6**），另设**阻断项**（验证未完成，如 E6 缺 `--dep`）

## 纪律

1. **卡死处理**：同一错误不重试超过 2 次；校验不过必须上报并给 2–3 个选项，不许死磕、不许静默跳过（跳过要留痕）。

3. **数据红线**：不编数据、不写未核实数据、不写客户隐私；不确定的一律标降级 + 说明。
4. **不承诺**：不承诺效果，不写「保证」「第一」。
5. **不引不存在的东西**：引用任何外部文件前，先确认版本号/章节号真实存在——这是全行业唯一被公开惩罚过的红线。
6. **交付后必须回流**：第 7 步不跳；学到的新判据当天写进脚本与回归。
7. **冻结纪律**：定稿后先清残留 → 跑全套门禁 → 算哈希 → 冻结（此后只读）→ 再转换格式；转换后登记「源稿哈希 → 产出哈希」。
